# Design: Bifrost Roadmap to 0.5.0

## Problem Statement

Bifrost v0.1.0 shipped with a solid core: Channel-based orchestration, autoscaling, resilience, health checks, OpenTelemetry, and event streaming. However, it lacks performance validation, documentation infrastructure, and several features needed by internal consumers (agentic-engine, AuthScript).

The path to 0.5.0 must accomplish three things: validate the performance claims made in the original design, add the capabilities internal projects need (dead letter queues, batch processing), and build the documentation and samples necessary for external adoption.

**Success criteria for 0.5.0:**
- Full BenchmarkDotNet suite validating zero-allocation hot paths
- VitePress documentation site with API reference and guides
- Dead letter queue support
- Batch processing support
- Priority queue support (if CPQ from DataFerry is performance-ready; otherwise deferred to 0.6.0)
- 80%+ test coverage maintained across all packages
- API surface stable enough for external consumers to adopt from NuGet

---

## Chosen Approach

**Foundation, Features, Validation (Layered)**

Build quality infrastructure first (benchmarks + docs scaffold), then ship features with confidence (each benchmarked and documented on arrival), then validate and stabilize for external adoption.

This approach front-loads the tooling so that every subsequent feature ships with performance data from day one. Performance regressions are caught immediately rather than discovered retroactively.

### Versioning

- **Pre-1.0 semver** — breaking changes allowed between minors
- **Ship when ready** — no fixed cadence
- **agentic-engine consumes NuGet releases** — each minor must be publishable

### 0.3.0 — Dead Letter Queues

Add dead letter queue support for failed work items. This is the most requested feature from internal consumers.

#### Design

**Core concept:** When a work item fails handler execution (throws, times out, exceeds retry count), it moves to a dead letter queue instead of being silently dropped.

**New types (Bifrost.Core):**

```csharp
public readonly record struct DeadLetteredWork<TWork>(
    TWork Work,
    Exception? Exception,
    int AttemptCount,
    DateTimeOffset FailedAt,
    string? CorrelationId);

public interface IDeadLetterQueue<TWork>
{
    ValueTask EnqueueAsync(DeadLetteredWork<TWork> item, CancellationToken ct = default);
    IAsyncEnumerable<DeadLetteredWork<TWork>> ReadAllAsync(CancellationToken ct = default);
    int Count { get; }
}
```

**Implementation (Bifrost):**

```csharp
// Channel-backed DLQ with configurable capacity
public sealed class DeadLetterQueue<TWork> : IDeadLetterQueue<TWork>
{
    private readonly Channel<DeadLetteredWork<TWork>> _channel;
    // ...
}
```

**Builder extension:**

```csharp
services.AddWorkOrchestrator<EmailJob>(opts => { ... })
    .WithHandler<EmailHandler>()
    .WithDeadLetterQueue(dlq =>
    {
        dlq.Capacity = 1000;          // DLQ buffer size
        dlq.MaxRetries = 3;           // Retries before dead-lettering
    });
```

**Integration points:**
- Works with `WithResilience()` — items dead-lettered after Polly retries exhausted
- Works with `WithEventStream()` — fires `WorkDeadLetteredEvent<TWork>`
- Works with `WithHealthChecks()` — DLQ depth health check
- Works with `WithOpenTelemetry()` — `orchestrator.items.dead_lettered` counter

#### Deliverables

- [ ] `IDeadLetterQueue<TWork>` abstraction in Bifrost.Core
- [ ] `DeadLetterQueue<TWork>` Channel-backed implementation
- [ ] `DeadLetterOrchestrator<TWork>` decorator
- [ ] `.WithDeadLetterQueue()` builder extension
- [ ] DLQ benchmarks added to suite
- [ ] DLQ health check in Bifrost.HealthChecks
- [ ] DLQ metrics in Bifrost.OpenTelemetry
- [ ] `WorkDeadLetteredEvent<TWork>` event type
- [ ] VitePress guide: `docs/site/guides/dead-letter-queues.md`
- [ ] Unit tests (target: 80% coverage on new code)

### 0.4.0 — Batch Processing

Add support for processing work items in batches rather than individually. Useful for database writes, API calls with batch endpoints, and bulk operations.

#### Design

**New handler contract:**

```csharp
public interface IBatchWorkHandler<TWork>
{
    ValueTask HandleBatchAsync(
        IReadOnlyList<TWork> batch,
        CancellationToken ct);
}
```

**Configuration:**

```csharp
services.AddWorkOrchestrator<DbRecord>(opts => { ... })
    .WithBatchHandler<DbBatchHandler>(batch =>
    {
        batch.MaxBatchSize = 100;                          // Max items per batch
        batch.MaxWaitTime = TimeSpan.FromMilliseconds(50); // Max wait to fill batch
        batch.MinBatchSize = 1;                            // Flush even partial batches
    });
```

**Implementation approach:** A `BatchingOrchestrator<TWork>` decorator that reads from the inner orchestrator's channel, accumulates items up to `MaxBatchSize` or `MaxWaitTime`, and dispatches to `IBatchWorkHandler<TWork>`. Uses `ChannelReader.ReadAllAsync()` with a timer-based flush to avoid holding items indefinitely.

**Key design decisions:**
- Batch size is a max, not a requirement — partial batches flush on timer
- Failed batches interact with DLQ — individual items from a failed batch can be dead-lettered
- Batch events report per-batch metrics (`WorkBatchCompletedEvent<TWork>`)
- Zero-allocation goal: pool the `List<TWork>` used for batch accumulation

#### Deliverables

- [ ] `IBatchWorkHandler<TWork>` contract in Bifrost.Core
- [ ] `BatchingOrchestrator<TWork>` decorator
- [ ] `BatchingOptions` configuration
- [ ] `.WithBatchHandler<T>()` builder extension
- [ ] Batch benchmarks (throughput vs individual, allocation validation)
- [ ] `WorkBatchCompletedEvent<TWork>` event type
- [ ] Batch metrics in Bifrost.OpenTelemetry
- [ ] VitePress guide: `docs/site/guides/batch-processing.md`
- [ ] Unit tests (target: 80% coverage on new code)

### 0.5.0 — Stabilization + Priority Queues

Final pre-1.0 stabilization pass. Complete documentation. Priority queues if CPQ is ready.

#### Priority Queues (Conditional)

**Gate:** Only included if the Concurrent Priority Queue from DataFerry meets performance requirements. If not ready, priority queues move to 0.6.0 and 0.5.0 focuses entirely on stabilization.

**Design (if included):**

```csharp
public interface IPriorityWorkOrchestrator<TWork> : IWorkOrchestrator<TWork>
{
    ValueTask EnqueueAsync(TWork work, int priority, CancellationToken ct = default);
    bool TryEnqueue(TWork work, int priority);
}
```

```csharp
services.AddWorkOrchestrator<AlertJob>(opts => { ... })
    .WithHandler<AlertHandler>()
    .WithPriorityQueue(priority =>
    {
        priority.Levels = 4;           // Number of priority levels
        priority.DefaultPriority = 2;  // Default when not specified
    });
```

**Implementation:** Replaces the single `Channel<TWork>` with N channels (one per priority level). Workers drain highest-priority channels first. Falls back to lower priorities only when higher are empty.

## Decorator Chain (Updated for 0.5.0)

```
┌──────────────────────────────────────────────────────────────────┐
│              Decorator Chain (0.5.0)                             │
├──────────────────────────────────────────────────────────────────┤
│  ┌────────────────────────────────────────────────────────────┐  │
│  │  ResilientOrchestrator            (order: 200)            │  │  ← WithResilience()
│  │  ┌──────────────────────────────────────────────────────┐  │  │
│  │  │  DeadLetterOrchestrator        (order: 150)          │  │  │  ← WithDeadLetterQueue()
│  │  │  ┌────────────────────────────────────────────────┐  │  │  │
│  │  │  │  AutoscalingOrchestrator    (order: 100)       │  │  │  │  ← WithAutoscaling()
│  │  │  │  ┌──────────────────────────────────────────┐  │  │  │  │
│  │  │  │  │  BatchingOrchestrator    (order: 75)     │  │  │  │  │  ← WithBatchHandler()
│  │  │  │  │  ┌────────────────────────────────────┐  │  │  │  │  │
│  │  │  │  │  │  EventStreamOrchestrator (order: 50)│  │  │  │  │  │  ← WithEventStream()
│  │  │  │  │  │  ┌──────────────────────────────┐  │  │  │  │  │  │
│  │  │  │  │  │  │  WorkOrchestrator  (order: 0) │  │  │  │  │  │  │  ← Core
│  │  │  │  │  │  └──────────────────────────────┘  │  │  │  │  │  │
│  │  │  │  │  └────────────────────────────────────┘  │  │  │  │  │
│  │  │  │  └──────────────────────────────────────────┘  │  │  │  │
│  │  │  └────────────────────────────────────────────────┘  │  │  │
│  │  └──────────────────────────────────────────────────────┘  │  │
│  └────────────────────────────────────────────────────────────┘  │
└──────────────────────────────────────────────────────────────────┘
```

**Ordering rationale:**
- **Resilience (200)** outermost — retries wrap everything, catches failures from any inner layer
- **Dead letter (150)** — catches items that exhaust retries, routes to DLQ
- **Autoscaling (100)** — collects metrics on actual work throughput
- **Batching (75)** — accumulates before event tracking for accurate batch-level events
- **Event stream (50)** — records events closest to actual execution
- **Core (0)** — Channel + worker pool, always innermost

## Open Questions

1. **DLQ persistence** — Should the DLQ support pluggable backing stores (file, database) in a future version, or is Channel-backed (in-memory) sufficient through 0.5.0?

2. **Batch failure granularity** — When a batch fails, should the entire batch go to DLQ, or should the handler be able to report which individual items failed?

3. **Priority queue starvation** — Should lower-priority items have a guaranteed minimum throughput, or is strict priority ordering acceptable?

4. **Docs deployment** — GitHub Pages, Netlify, or Cloudflare Pages for the VitePress site?

5. **Benchmark CI gating** — Should benchmark results gate PRs (fail if regression detected), or remain informational?
